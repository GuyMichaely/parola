# Noun morphology and answer syntax

Parola keeps a noun's stored morphology separate from the study syntax used to recognize typed answers.

## Noun cards

A noun card stores four morphology facts:

- `rule`, the name of its declension rule;
- `base`, the string transformed by that rule;
- `gender`;
- `articleMode`, currently `automatic` or `none`.

It does not store singular/plural strings, articles, or a separate number mode. Those are derived from the referenced declension rule.

For example:

```json
{
  "type": "noun",
  "english": "mirror",
  "italian": "specchio",
  "details": {
    "rule": "-chio -> -chi",
    "base": "spec",
    "gender": "masculine",
    "articleMode": "automatic"
  }
}
```

The actual default rule name uses the Unicode arrow: `-chio → -chi`.

## Declension rules

A declension rule has a unique name and one or two supported number forms. The name is also its reference. There is no separate rule ID.

```json
{
  "name": "-o → -i",
  "forms": {
    "singular": { "suffix": "o" },
    "plural": { "suffix": "i" }
  }
}
```

The presence of form entries defines number availability:

```text
singular + plural entries  -> both numbers
singular entry only        -> singular only
plural entry only          -> plural only
```

For example, `Plural form is the base` contains only:

```json
{
  "name": "Plural form is the base",
  "forms": {
    "plural": { "suffix": "" }
  }
}
```

A blank suffix means the base itself is the surface form. `base: "vestiti"` therefore produces `vestiti`, and there is no singular form to derive.

Generation and recognition use the same rule definition. A supported form is generated by appending its suffix to the base. Recognition reverses that operation by removing the configured suffix. A missing form is unsupported.

A rule name must be unique. Renaming a rule in the morphology editor updates references in inference sets and noun cards when the morphology change is saved.

## Why number is not stored on noun cards

The rule already answers the question. A card that references `-o → -i` has both numbers because that rule contains both form entries. A card that references `Plural form is the base` is plural-only because the rule contains only a plural entry.

This keeps one source of truth. A noun cannot separately claim to be plural-only while referencing a two-number rule.

Examples:

```text
cetriolo: rule -o → -i, base cetriol                 -> cetriolo / cetrioli
specchio: rule -chio → -chi, base spec               -> specchio / specchi
Venezia: rule Singular form is the base, base Venezia -> Venezia only
clothes: rule Plural form is the base, base vestiti   -> vestiti only
```

`dress` and `clothes` remain different noun definitions even though `vestiti` appears in both paradigms:

```text
dress:   rule -o → -i, base vestit
clothes: rule Plural form is the base, base vestiti
```

## `articleMode` on noun cards

`articleMode` controls whether Parola generates article forms for that noun.

`automatic` means Parola chooses articles from gender and spelling, such as `lo specchio`, `gli specchi`, and `uno specchio`.

`none` means the card has no generated article forms. `Venezia` is an example in the current inventory model.

The card does not store the article strings themselves.

## Inference sets

An inference set is a named study-policy group. Its name is also its reference. There is no separate inference-set ID.

```json
{
  "name": "Learned shorthand",
  "declensionRules": [
    "Unchanged singular / plural",
    "-o → -i",
    "-e → -i"
  ]
}
```

Each entry is the name of a declension rule. Several syntax rules can use the same inference set.

Renaming an inference set in the morphology editor updates syntax references at the same time.

The `specchio` learning-policy case depends on this separation. The `-chio → -chi` rule can exist and be assigned to the `specchio` card while remaining absent from `Learned shorthand`. Adding it to that inference set later changes what shorthand can infer without changing the card.

## Syntax rules

A syntax rule describes a typed noun-answer structure. Syntax names are unique and serve as their identity in diagnostics and editing.

A syntax contains:

- `name`;
- optional/required markers;
- ordered input fields;
- `numberMode`, which selects rules with the corresponding form availability;
- `articleMode`, which currently controls article generation for candidates produced by that syntax;
- `inferenceSet`, the name of the inference set it uses.

For example, `Article + singular` contains:

```text
[gender] <definite singular article> <singular noun>
```

`Gender + singular` contains:

```text
<gender> <singular noun>
```

Both use `Learned shorthand`.

Syntax `numberMode` remains separate from noun-card storage because it is parser policy. It decides which declension rules a syntax is allowed to try. A `both` syntax tries two-number rules. A singular-only syntax tries rules with only a singular form. A plural-only syntax tries rules with only a plural form.

Syntax rules can also require singular-only or plural-only markers. Marker order is currently flexible.

### Current syntax `articleMode` behavior

The syntax parser currently uses `articleMode` in two ways:

1. If the syntax contains article fields, it generates the expected articles and checks the typed article tokens against them.
2. It puts the syntax's `articleMode` on each morphology candidate, and final candidate equality compares that value with the card's stored `articleMode`.

The second behavior means a syntax without an article field can still constrain which noun cards it matches. For example, `Gender + singular` currently produces `automatic` candidates even though the learner did not type an article.

This is current behavior, not a claim that `articleMode` must remain part of syntax definitions. The card-level article property and the evidence supplied by a syntax are distinct modeling questions.

## Candidate parsing

Parola does not choose one declension before checking an answer. It preserves every applicable interpretation.

For each noun answer:

1. Try every syntax rule against the typed tokens.
2. For each structurally complete syntax, load its inference set.
3. Try each declension rule in that set whose supported forms match the syntax number mode.
4. Let the rule recognize the typed noun fields and infer a base.
5. Use explicit gender/article evidence to reject contradictions or branch ambiguous facts.
6. Produce morphology candidates.
7. Only after parsing, compare those candidates with the prompted card.

The target card is not consulted while generating candidates.

The result follows three rules:

- Any matching candidate means correct.
- If no candidate matches but at least one syntax is structurally complete, the answer is wrong.
- If no syntax is structurally complete, the input is invalid or incomplete.

A complete syntax can therefore be wrong even when its inference set produces zero candidates.

## Example: `specchio`

Suppose the card is:

```text
rule: -chio → -chi
base: spec
gender: masculine
articleMode: automatic
```

Suppose `Learned shorthand` initially contains `-o → -i` but not `-chio → -chi`.

For `lo specchio`, `Article + singular` is structurally complete. `-o → -i` recognizes the final `o` and produces base `specchi`. That candidate does not match the card's rule/base, so the answer is wrong.

For `m specchio`, `Gender + singular` follows the same inference-set policy. It likewise cannot produce the card's `-chio → -chi` candidate yet.

After `-chio → -chi` is added to `Learned shorthand`, either input can also produce base `spec` under that rule. That candidate matches the card.

## Names as references

Declension rules and inference sets no longer carry a separate machine ID plus a display name. Their unique names are the references.

This makes the persisted model smaller:

```text
noun card          -> rule name
inference set      -> declension rule names
syntax rule        -> inference-set name
```

The editor treats renaming as a structural operation and updates those references before saving. Duplicate names in the same collection are rejected.

## Live preview

The live preview shows the selected syntax, consumed fields, missing fields, and any declension names inferred from that selected syntax.

Candidate generation does not consult the prompted card's stored rule/base, so the preview must not identify which candidate is the correct one before submission.

## Inventory state

Cards and noun morphology form one inventory state:

```json
{
  "cards": [],
  "nounMorphology": {
    "declensionRules": [],
    "inferenceSets": [],
    "syntaxRules": []
  }
}
```

Storage validates the snapshot as a whole. Every noun must reference an existing rule, and its stored primary `italian` value must equal the primary form generated from its rule and base.

Browser persistence stores the inventory with its synchronization timestamp. The API stores the same complete state.
